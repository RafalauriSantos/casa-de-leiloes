## D1. Stack and hosting
- **Chosen:** React + Vite + TypeScript (front); Node.js + TypeScript + Hono (back); Postgres and Auth on Supabase; one Vercel project serving the static site and the API on the same origin (`/api/*`); `pg` as driver through the Supabase transaction pooler (port 6543).
- **Why:** the brief requires "NodeJS or Python" and leaves the framework open. Node on Vercel is the native runtime. One language on both sides.
- **Tradeoff:** Hono is less known than Express; only `routes` depends on it, so swapping it is cheap. Cloudflare Workers was rejected: it is not literally Node.js and the brief says NodeJS.
- **Layout on Vercel:** one project using Vercel Services in `vercel.json`: `frontend/` as the site, `backend/` as the API, rewrite `/api/(.*)` to the backend and everything else to the frontend (documented by Vercel). The Hono app is exported with `export default app` from a supported entry file.
- **Dropped connections:** the pool has an `error` listener (idle clients) and `tx()` attaches one to the borrowed client, because node-postgres emits `error` on the client out of band and an unhandled one would terminate the API. A transaction cut by a dropped connection fails with an error, the broken client is discarded, and only the error message (never the error object, which can carry the password) is logged. Tests kill real backends with `pg_terminate_backend`, idle and mid-transaction.
- **Pooler rules:** the transaction pooler (port 6543) does not support prepared statements and shares connections between clients, so code uses only `BEGIN/COMMIT` and `SET LOCAL`, never session-level `SET`. `pg` sends unnamed queries by default, which is compatible.
- **Proven in the walking skeleton (slice 0):** the Vercel Services layout with Hono (the service keeps the original `/api/...` path), the Supabase transaction pooler with a 20-way row-lock test, signup then `/api/me` on the deployed site, and `pg_cron` + `pg_net` on the free plan. Still to observe over days: whether the free project is paused for inactivity.
- **TLS to the pooler:** Node's `pg` treats `sslmode=require` as full verification, and the Supabase pooler chain is signed by Supabase's own root. The backend embeds the public Supabase Root 2021 CA (fingerprint recorded in `shared/supabase-ca.ts`, checked against the chain the pooler serves) and verifies the server instead of disabling checks.
- **Vercel build:** the frontend builds with `vite build` only and the backend has no build script (Vercel builds it); type checking stays in `make ci`, because Vercel installs only the service's dependencies and has no `tsc` there.

## D2. Architecture: modular monolith with a functional core
- **Chosen:** one deployable, split by feature (`bidding`, `wallet`, `lots`, `settlement`, `audit`, `catalog`, `identity`). Each module has `rules.ts` (pure functions, the clock is a parameter), `service.ts` (transaction + SQL) and `routes.ts` (HTTP). A module exposes only its `index.ts`.
- **Enforced in `make ci`:** ESLint `no-restricted-imports` blocks reaching into another module's internals and blocks `pg`, `fetch` and `Date` inside `rules.ts`.
- **Why:** the money guarantee lives in Postgres locks and constraints. A repository interface would hide the lock order and, since fakes are banned (D12), no test would use it.
- **Tradeoff:** services are coupled to Postgres on purpose; changing database means rewriting SQL.

## D3. Data model
- `profiles(id = auth.users.id, role auctioneer|bidder, display_name)`; role comes from this table. A trigger creates profile and wallet on sign-up; it reads the role chosen at sign-up once, at creation (D24), and later metadata edits change nothing.
- `wallets(user_id, total_cents, committed_cents)` with `CHECK (committed_cents >= 0 AND total_cents >= committed_cents)`; available = total - committed.
- `wallet_ledger(user_id, kind deposit|lot_debit|lot_credit, amount_cents, lot_id, idempotency_key)`; unique `(lot_id, kind)` for settlement kinds and unique `(user_id, idempotency_key)` for deposits.
- `lots`: auctioneer, status `active|cancelled|integrity_cancelled` (a lot is settled when `settled_at` is set; `integrity_cancelled` is the owner's release of D20), outcome `sold|no_bids`, item snapshot, `starts_at`, `ends_at`, `starting_bid_cents`, `increment_cents`, plus `current_amount_cents`, `leader_id`, `bid_count`, `head_seq`, `head_hash`, `settled_at`. "Scheduled" and "live" are derived from the clock, not stored. *Replaces the original list `active|cancelled|settled`: the code has always marked settlement with `settled_at`.*
- `bids(lot_id, seq, bidder_id, amount_cents, placed_at, prev_hash, hash)` unique `(lot_id, seq)`; a trigger rejects UPDATE/DELETE (defence in depth, not security).
- `receipts(code, lot_id unique, winner_id, amount_cents, head_seq, head_hash, closed_at)`; `code` is random.
- `wallet_ledger` is append-only for every normal connection: a trigger refuses update, delete and truncate (the table owner could still disable the trigger deliberately), and a user with money history cannot be deleted because of a foreign key. `display_name` (user-editable sign-up metadata) is capped at 80 characters by the trigger, and the trigger functions are not executable by the API roles.
- RLS enabled on every table with no policies: Supabase's REST layer exposes nothing; only our API reads the database.
- **Tradeoff:** `lots` duplicates the current bid for fast reads; it is written in the same transaction as the bid, and a test recomputes it from `bids`.

## D4. Tamper-evident bid history (keyed hash chain)
- **Chosen:** `hash_n = HMAC(SECRET, "v1|lot_id|seq|bidder_id|amount|placed_at_utc|hash_(n-1)")`; first `prev_hash = HMAC(SECRET, "genesis|lot_id")`. `AUDIT_HMAC_SECRET` lives only in the server environment. The receipt stores the final `head_seq` and `head_hash`.
- **Detection by recomputing the chain:** edited value or author (hash differs at that seq), deleted in the middle (seq gap and broken `prev_hash`), inserted (no secret, no valid hash), reordered (seq and `prev_hash` stop matching).
- **Last bid removed:** the rest of the chain stays valid, so the chain check does not catch it, and the head copy in `lots.head_*` can be rewritten with it. Detection needs a copy of the head outside the database, as decided in D21.
- **Gap against the brief, not an accepted limit:** someone with full database access can delete the last bid and rewrite `lots.head_*` to the previous valid state. The brief requires this to be detected: section 03 (Back-End), "Histórico à prova de adulteração", says any change, removal or insertion must be detected, including directly in the database (checked on page 4 of `.local/enunciado.pdf`). D21 narrows it to the publication window declared in D21 and D22 (a last bid removed before its hash is published). Until D21 is built, the gap stays fully open, and the README must declare it before submission. *Replaces the earlier "known limit" wording, which accepted the removal of the last bid as a limit.*
- **Tradeoff:** it is keyed, so third parties cannot verify on their own; the server verifies. Rotating the secret makes every existing chain look tampered, so there is no rotation. The hash covers the time to the millisecond, while `placed_at` keeps microseconds: a stored time with a part finer than a millisecond was not written by the bid path, and it counts as a break at that bid (`shared/bid-history.ts` reads it with the bids), so a change of a few microseconds cannot hide.

## D5. Concurrency of bids and committed balance
- **Chosen:** one transaction per bid: `SELECT ... FOR UPDATE` on the lot (serializes bids of the same lot), then lock the bidder's and the previous leader's wallets in `user_id` order (avoids deadlock across lots), read the database clock after the locks, validate, release the previous leader, commit the new one, append the bid with its hash, update the lot, apply anti-sniping.
- **Anti-sniping (literal reading of the brief, chosen by the owner):** if `ends_at - now <= 2 min` then `ends_at = ends_at + 2 min`. A bid at exactly `ends_at` is refused. Extensions are unbounded (README). This replaces the earlier rule `ends_at = max(ends_at, now + 2 min)`, which the owner set aside in favor of the brief's wording.
- **Proof:** parallel HTTP requests against real Postgres; afterwards seqs are contiguous, the chain is valid, `committed` equals the recomputed value and nobody is negative. The `CHECK` is the second barrier.

## D6. Closing and settlement
- **Chosen:** `settleLot(lot_id)` in one transaction: lock the lot; if `settled_at` is set or `now < ends_at`, do nothing (idempotent); no bids means `no_bids`; otherwise debit the winner (total and committed), credit the auctioneer, write two ledger rows and create the receipt. Outbid bidders were already released when they lost the lead.
- **Triggers:** on demand, built: reading a lot (public page or live room), bidding, and reading the wallet of a leader settle the due lots involved, so a lot closes when it is looked at. A failure there is logged and does not fail the reader; the cron still reports it with HTTP 500. The chain check lives in `shared/bid-chain.ts`, so both bidding and settlement can use it without a module cycle; plus Supabase `pg_cron` + `pg_net` calling `POST /api/internal/close-due` every minute with `CRON_SECRET`, so lots close with nobody looking.
- **Planned (D22):** the audit route will never settle a lot, unlike the reads above.
- **Built (D21, the owner's option B):** settlement also waits for the lot's last head to be published in the public anchor. Under the lot's row lock, after the history is known to be intact, a lot with bids whose `anchored_seq` is below its `head_seq` is not settled: nobody is charged, nothing is credited, the committed money stays, and it is not a failure (the next run tries again). `anchored_seq` is read, and the GitHub file is not read inside the settlement, so the lot is not held for a 4-second call; the publisher raises `anchored_seq` only after the file is written, and the audit compares the file with it afterwards (a lot that says it was published and whose file lacks a bid is `divergent`), so a database writer who only raised the number would be seen. A lot with no bids has nothing to publish and a lot of an environment with `ANCHOR_MODE=off` has no public anchor, so neither waits. What the settlement checks is the history (the chain and the lot's head copy) and `anchored_seq`; it does not read the anchor file. A lot whose file was altered or deleted on GitHub after the publisher raised `anchored_seq` and before the settlement runs (a window of about a minute, for someone with write access to the anchor repository) is seen as `divergent` by the audit, but is still paid: the audit shows it afterwards, the settlement does not stop it. Stopping it would need the settlement to read the file under the lot's lock, which the owner declined. The release of D20 (built, run by the owner) covers only a lot whose history fails verification or whose copy disagrees with its last bid. An anchor that contradicts an intact history has no release yet: a declared limit that needs a new decision. *Changes the settlement rule above (D21).*
- `pg_net` is asynchronous and its request timeout defaults to 2000 ms, so the job sets `timeout_milliseconds` explicitly and ignores the response; the endpoint itself is idempotent.
- The per-minute call is also application traffic to the database, which counts as activity against Supabase's free-plan inactivity pause (to be observed, not assumed).
- **Fallback if `pg_cron` fails in slice 0:** GitHub Actions every 5 minutes.
- **Tradeoff:** extra moving parts (two extensions, one secret) for punctuality only.

## D7. Real-time: polling
- **Chosen:** `GET /api/lots/{id}/live` every 3 s (the 1-2 s first approved was left open to be fixed in this phase; 3 s keeps one viewer under the free database query budget), a single query, returns `server_now` so the countdown uses the server clock; pauses when the tab is hidden; backs off on errors and shows a connection warning instead of faking "live".
- **Why not Supabase Realtime / WebSocket / SSE:** Realtime would expose tables to clients (privacy, RLS); WebSocket and SSE fight serverless time limits.

## D8. External API and snapshot
- **Chosen:** Met Museum Collection API (`/v1.1/search`, `hasImages=true&isPublicDomain=true`). Search returns only ids; the server fetches the first 12 details in parallel (5 s timeout). The Art Institute of Chicago was rejected: automated requests got a 403 Cloudflare challenge.
- **Snapshot:** the client sends only `external_id`; the server refetches and copies title, artist, date, medium, department, source link and image URL into `lots.item_*`. Never trust item data sent by the client. After creation nothing depends on the API (image is stored as a URL; if the image fails to load, its alt text (the item title) stays visible).
- **Outage:** search returns `503 catalog_unavailable`; no half-created lot; showcase, rooms, audit and receipts keep working.
- **Tradeoff:** images are hotlinked, so the lot loses its picture if the museum's image host is down.

## D9. API contract and the single error shape
- Error body is always `{ "code": "...", "message": "..." }` (the one exception is the cron answer `{ settled, failed, anchor }`, accepted by the owner on 2026-10-24, D21); framework validation errors are mapped to it.
- Codes: `validation_error` 422, `bid_below_minimum` 422, `unauthenticated` 401, `forbidden` 403, `not_found` 404, `insufficient_funds` 409, `already_leading` 409, `bid_limit_reached` 409 (the lot already has 1,000 bids, D23), `lot_not_started` 409, `lot_ended` 409, `lot_not_editable` 409, `idempotency_conflict` 409, `catalog_unavailable` 503, `internal_error` 500 (no stack or database message leaks).
- Public: `GET /api/lots?status=&q=`, `GET /api/lots/{id}`, `GET /api/lots/{id}/live`, `GET /api/lots/{id}/audit`, `GET /api/receipts/{code}`.
- Bidder: `GET /api/me`, `GET /api/wallet`, `POST /api/wallet/deposits` (requires an `Idempotency-Key` UUID: 201 on the first request, 200 replaying the same key, 409 `idempotency_conflict` if the key is reused with another amount; the ledger has a unique index on `(user_id, idempotency_key)` and the balance is changed with an atomic `total_cents = total_cents + n`), `POST /api/lots/{id}/bids`, `GET /api/me/wins`.
- Auctioneer: `GET /api/catalog/search?q=`, `POST /api/lots`, `PATCH /api/lots/{id}`, `POST /api/lots/{id}/cancel`, `GET /api/auctioneer/lots`, `GET /api/auctioneer/summary`.
- Internal: `POST /api/internal/close-due` (Bearer `CRON_SECRET`).
- Identity always comes from the JWT; ownership is checked on every auctioneer route.

## D9b. My wins and the win receipt (J6)
- `GET /api/me/wins` (bidder only, from the token): the lots the bidder won first, then the others by newest bid, at most 100 lots. A GET settles the ended lots this bidder leads, one at a time, before listing (D6): with many such lots the request is slower, and a timeout leaves the unsettled lots unsettled, never half-done. Each lot carries the outcome, the bidder's highest offer and, when they won, the receipt code.
- Outcome rule (`receipts/rules.ts`, pure): a receipt for the bidder means `won`; a lot that is not active means `cancelled`; a lot still running shows `leading` or `outbid`; an ended lot without a receipt shows `lost`, or `settling` when the bidder led at the end (the settlement waits for the publication of the last bid, D21). `settling` is shown as "Encerrado, aguardando o comprovante" with a refresh: it is held while the settlement is not done (a broken history, an anchor wait), so it is never shown as won.
- `GET /api/receipts/{code}` is public by its random 128-bit code (D10). It names the winner by pseudonym only and carries no user id or e-mail.
- Declared limit: more than 100 lots are not shown and the page says nothing about the rest. The screen's error and retry path is not covered by a test: proving it needs the list request to fail, which the project only simulates for the live check.
## D9c. Demo data (B2, criterion 8.1)
- `make seed` (CLI `backend/scripts/seed.ts`, logic in `src/seed/demo.ts`) creates one auctioneer, two bidders with balance and one live lot with three bids. Accounts are real Auth users, deposits and bids go through the API with fixed keys, so a second run changes nothing (tested).
- **Exception to "no default secrets":** the demo accounts share one password, written in the README, because the brief asks for test credentials there. It is used only by these three accounts, and the seed refuses nothing else. The owner chose this on 2026-10-26.
- The lot's item is copied in at the seed, as for every lot; the seed does not call the external catalog.
- **Two more demo lots (B17, B18, 2026-10-26):** an ended lot that bidder 1 won, with its receipt, so "Meus arremates" and the receipt link work right after the seed; and a settled lot whose first bid the seed overwrites in the database, past the update trigger (`session_replication_role = replica`), so the audit shows "adulterado" without anyone touching the database. Both take real bids through the API; their end is then moved to now in the database and they are settled on demand. Where the anchor is on, the settlement waits for publication (D21), so the seed waits up to 5 minutes and stops with an error after that. The tampering runs only after the settlement, so no money and no pending publication depend on it. Not verified on the hosted project: whether its `postgres` role may set `session_replication_role`; if not, the seed stops with that error.
- **Login shortcuts (B15, 2026-10-26):** the login screen offers the three demo accounts. Each shortcut is a real sign-in with the shared password, which now also ships in the site's code (`DEMO_ACCOUNTS` in the contracts, used by the seed and the screen). That exposes nothing new: the README already publishes it, and it opens only these three accounts. A failed shortcut says the demo account is not available, never a fake session.

## D10. Privacy
- Pseudonym = `HMAC(SECRET, "pseudonym|lot_id|user_id")` shortened: stable inside a lot, different across lots. Never name, email or id; the logged-in user sees "you".
- Public bid times are shown truncated to the second (the hash uses the exact value; the server verifies). Documented in the README as the indirect-identification tradeoff.
- Receipt `code` is random (128 bits); the receipt shows the pseudonym only.

## D11. Auth
- Supabase Auth; the backend validates the JWT against the project's JWKS (`jose`, issuer, `authenticated` audience and an ES256/RS256 allowlist checked). A bad, expired or foreign token is a 401; the key server being unreachable or answering garbage is a 500, never "log in again". Tests sign real tokens against a real key server for each claim rule. Supabase's default signing is HS256, which the JWKS endpoint cannot verify, so asymmetric signing keys must be enabled in the hosted project (and checked in local `supabase start`) in slice 0; email confirmation is off, both locally (default) and in the hosted project (Confirm email toggle; the hosted default is on and the built-in mailer allows only a few messages per hour, so sign-up fails with `over_email_send_rate_limit` until it is off; hosted Auth also rejects reserved domains such as `example.com` in e-mails); profile and wallet are created by a trigger. Session stays in `localStorage` (Supabase default; XSS exposure to be declared in the README; the CSP and security headers are set in `vercel.json` (see the README)).

## D12. Tests: real, no mocks or fakes
- Real Postgres (`supabase start`) with the real migrations, real Supabase Auth, real HTTP server called with `fetch`, real parallel requests, real clock (short lots of 2-3 s; anti-sniping uses a lot ending in 90 s). The seed (planned, slice 6) goes through the same services.
- The Met and, from D21, the GitHub anchor repository are the external systems stubbed in CI: the production client reads responses captured from the real API and served by a local HTTP server; outage is a closed port. `make e2e-live` (slice 2) hits the real Met (not in `make ci`; run before each deploy and before submitting).
- Planned (slice 6): a full-journey script against the deployed URL after each deploy, with disposable `e2e-` users. Until then the deployed app is checked by hand and with the curl checks recorded in each slice's PR.
- `make ci` runs lint, typecheck, build, tests with coverage gates (backend 95% statements/lines and 90% branches/functions; frontend 85/80/85/85) and `npm audit` on production dependencies (high severity fails); it is exactly what GitHub Actions runs.
- Frontend tests start the real backend (global setup) and drive the real UI against real Supabase Auth and Postgres, so the journeys (sign-up, wallet, double-click deposit, role guard) are end to end without mocks.
- Working rule of the author: every push is preceded by `make ci` and a read-only review by a `pr-reviewer` agent (a local tool, kept outside the repository); findings are tiered Blocking/Important/Minor and fixed before pushing.

## D16. File organization
- npm workspaces: `frontend/`, `backend/`, `packages/contracts/` (error codes, `{code, message}` shape and endpoint DTOs, types only, so front and back cannot drift); `supabase/migrations/` (one migration per concern, never edited after being applied); `docs/`.
- Backend: `src/create-app.ts` (builds the Hono app; not named `app.ts` because Vercel would pick that name as the entry point) and `src/index.ts` (the Vercel entry, default export), `src/config.ts` (the only place that reads env vars, fails on startup, no default secrets), `src/shared/` (`db`, `errors`, `auth`, `money`), `src/modules/<feature>/` with `index.ts`, `routes.ts`, `schemas.ts`, `service.ts`, `rules.ts`. Unit tests sit next to the code (`rules.test.ts`); integration and end-to-end tests live in `backend/tests/`.
- Frontend: `app/` (router, providers), `pages/` (thin, compose features), `features/<name>/` (components, hooks, `api.ts`, `index.ts`), `components/ui/`, `lib/`, `styles/`. A feature imports another only through its `index.ts`.
- Conventions: `kebab-case` files (React components in `PascalCase.tsx`), split a file past ~200 lines, no catch-all `utils.ts`, SQL only in `service.ts`, `@/` import alias in the frontend only; the backend uses short relative imports (Vercel bundles the function itself, and the module-boundary lint rule keeps imports shallow).
- Tradeoff: three workspaces and one shared package add setup in slice 0 in exchange for one source of truth for the API contract.

## D17. Slice 2: catalog and lots (as built)
- **Catalog adapter** (`modules/catalog/met-client.ts`): the Met's public API. Search (`/v1.1/search`, images and public domain only) returns ids; the first 12 are fetched in parallel with a 5 s timeout. Items that are not public domain or have no image are skipped, never shown broken. Any detail that fails (network error, timeout, 5xx or unexpected body) fails the whole search with `503 catalog_unavailable`: a shorter list would look like a complete answer (no fail-open). Only an item the catalog does not have (404) is left out.
- **Copy, not reference:** creating a lot sends only `externalId`; the server fetches the item and copies title, image URL, source URL and attributes into the lot. If the catalog fails, nothing is written (tested by counting rows). Afterwards the lot never reads the catalog.
- **Derived states:** `scheduled`, `live`, `ended` come from the database clock: start inclusive, end exclusive (exact boundaries unit-tested). `cancelled` is stored.
- **Rules (pure, `modules/lots/rules.ts`):** create needs a start in the future and a duration of at least one minute; edit only before the start and without bids; cancel only without bids and before the end (the planned exception is the integrity cancel in D20). The bid count is `bid_count`, kept at zero until the bidding slice maintains it. *Adds the planned exception of D20; nothing is replaced.*
- **Ownership:** an auctioneer edits or cancels only their own lots: `403 forbidden` for someone else's lot, `404` for an id that is not a lot.
- **Showcase:** public, no login; cancelled lots are hidden from everyone but their owner; at most 60 lots per list. Unfiltered, live and scheduled lots come first (soonest-ending first) and ended lots last; the ended tab shows the most recently ended first. The start rule is checked in the application and again inside the insert (a database guard, tested by holding a table lock until the start passes). Title search escapes `%` and `_`.
- **Times:** the UI sends a Brazilian wall-clock time with the explicit `-03:00` offset; the server stores UTC; the screens show `America/Sao_Paulo`.
- **Test catalog:** tests use real responses captured from the Met (`backend/tests/fixtures/met`) served by a local stub, so CI never depends on the internet. `make e2e-live` calls the real Met (not part of `make ci`).

## What stays simulated (declared in the README)
Deposits (no real payment), email confirmation off, polling instead of push.

## D18. Slice 3: bids and the live room (as built)
- **Rules are pure** (`modules/bidding/rules.ts`): `decideBid(lot, wallet, bid, now)` returns the verdict and the money to release; the clock is a parameter read from the database after the locks.
- **One transaction per bid:** lock the lot (`for update`), then lock the bidder's and the previous leader's wallets in user-id order, read the clock, decide, release the previous leader, commit the bidder, append the bid with its hash, update the lot. Lock order is fixed, so two lots and two bidders cannot deadlock.
- **Hash chain** (`shared/bid-chain.ts`): HMAC-SHA256 with the audit secret over the lot, sequence, bidder, amount, time (ISO with milliseconds, the stored precision) and the previous hash; the genesis is per lot. The `bids` table refuses update, delete and truncate. The lot keeps a copy of its head (`head_seq`, `head_hash`) for speed; settlement and the audit must check those copies against the chain and not trust them alone.
- **Privacy:** public responses carry pseudonyms (HMAC of lot and user, 12 hex characters) and never user ids; `mine` marks the viewer's own bids.
- **Position:** `leading`, `outbid` (asked of the whole history, not the window shown) or `none`, for a signed-in viewer only.
- **Not idempotent by design:** a repeated bid from the leader is refused with `already_leading`; a retry after a lost response is refused the same way.
- **Clock for the screen:** the room polls every 3 s, reads the server clock at the midpoint of each request, ignores answers older than the newest applied or started before the last bid's answer, and never runs two reads at once.
- **Tests:** rules and chain as unit tests; integration on real Postgres: exact messages, funds boundaries, anti-sniping boundaries, the hash chain recomputed from rows, the append-only trigger, and concurrency (20 bidders at once, one user firing ten, one balance in two lots, bids crossing between two lots) with invariants on the committed money. Mutation check: removing the row locks makes four of the concurrency tests fail.

## D19. Quality bar per phase (what "tested well" means here)
Each item is measurable. A phase closes only when its items are met and the evidence is in the PR.

**Phase 6, build by slice (every slice):**
- **Traceability:** every acceptance criterion of the slice (J0..J8, the brief's journeys from phase 2 of the delivery process) maps to at least one test with a stable name. The map lives in `docs/TRACEABILITY.md`; a criterion with no test is listed as open, never silently skipped.
- **Real dependencies:** business rules and error paths run on real Postgres, real Auth and real HTTP. No mocks or fakes in the repository's tests.
- **Money paths:** at least 20 simultaneous requests for each path that moves money, with invariants checked afterwards (no negative balance, committed money equals the leader's amount, contiguous sequence numbers, no lost update).
- **No fixed waits:** tests wait for a condition with a timeout, never for a fixed number of milliseconds.
- **Stability:** the suite passes on 10 consecutive runs before a slice closes.
- **Browser flow in CI:** at least one happy path and three refusal paths per slice run in a real browser on every push.
- **Review:** the clean-context reviewer returns PASS on the staged diff, and the report lists what was not verified.

**Phase 7, harden (before delivery):**
- **Mutation:** a mutation tool kills at least 80% of injected defects in the money modules (wallet, bidding, settlement). The score is recorded in CI.
- **Accessibility:** zero critical or serious violations on each screen, checked automatically.
- **Load:** the bid endpoint answers with no 500 and no broken invariant under the target load, with a response-time budget recorded.
- **Security:** dependency audit at zero high-severity findings; authorization and token-claim tests; row-level-security tests for every table.

**Phase 8, deliver:**
- A journey script runs against the deployed URL after each deploy.
- Traceability covers 100% of the brief's criteria, or each gap is declared in the README.

**Current status (recorded when this decision was written):** slice 3 meets the no-mock item, and the 20-request item only for the multi-bidder path (20 bidders at once). Its other money paths use 2 to 12 simultaneous requests. It does not yet meet the traceability, browser-flow, mutation, accessibility, load, fixed-wait and full concurrency items. Those gaps are the next work.

## D20. A lot with tampered history: release by a person's decision
- **Chosen:** a lot whose history fails verification is never settled and never paid (built, D6); a lot whose head is `divergent` from the anchor (D22, D21) is meant to be held the same way (planned: today the settlement does not read the anchor file, see D21). Its committed money stays committed until the system owner decides. The decision can then cancel the lot without a sale and release the winner's committed money back to the available balance. No one is charged, and the auctioneer receives nothing.
- **Who decides:** the system owner (the project owner, with access to the privileged database connection), not the API. There is no app endpoint for it, so no bidder, auctioneer or public caller can trigger it. The release is one transaction: it sets the lot's status to `integrity_cancelled`, decreases `wallets.committed_cents` of the winner, and inserts one row in an append-only table `integrity_decisions` (lot, decided by, decided at, reason, the broken sequence number). It leaves `lots.outcome` null and `lots.settled_at` null, because no sale happened.
- **Evidence:** nothing public shows the head hash (`lots.head_hash`, called "ponta" in the log message), and a tampered lot has no receipt, because receipts are written only by a successful settlement (D6). Today the only signal is the lot id in the log and the HTTP 500. The verification reports the first broken sequence number (`firstBrokenSeq`, D4), stored in the decision row. A head hash that a user kept (the audit page's `?head=`) is a second source.
- **Not chosen:** automatic release on detection. A bug in the check or a bad migration would then release a healthy lot, and a release decided without evidence cannot be undone for the auctioneer.
- **Not chosen:** settling the verified part of the history. Paying on a history known to be altered is the worst outcome.
- **Until the decision:** the lot stays `active` and unsettled, and the cron keeps reporting it with HTTP 500 every minute (D6, the close-due route). That is intended: it is an open incident, not a success. A lot with a pending head (D21) is not an incident and is not counted as a failure until its oldest unpublished bid has waited 10 minutes (D21).
- **Tradeoff:** the system cannot tell tampering from a bug on its own, so when tampering is confirmed the auctioneer loses the sale. The auctioneer must be told why the lot was cancelled.
- **Relation to earlier decisions:**
  - It is an explicit exception to the cancel rule in D17 ("cancel only without bids and before the end"). It applies only to a lot whose history failed verification, after the system owner's decision. The lot's auctioneer keeps the D17 rule for their own cancel.
  - It does not use the stored `cancelled` status, which the showcase hides from everyone but the lot's auctioneer (D17). The status is shown to the auctioneer as cancelled. The audit answer does not show the status yet: a released lot's audit still answers its history. The showcase's ended tabs do not list it.
  - Releasing committed money does not change `total_cents`, so no ledger row is written. The decision is recorded in `integrity_decisions`, which is an audit event and not a ledger kind (D3 keeps the ledger kinds fixed).
  - The committed-money recompute (D5, D18) must skip `integrity_cancelled` lots, or it will report a broken invariant.
- **Status (built, 2026-10-25):** the release is `releaseTamperedLot` (`modules/settlement/release.ts`), run by the owner with `backend/scripts/release-lot.ts` and the privileged connection; there is no endpoint. The script shows the lot's own copy of the leader and amount next to the last stored bid, asks the owner to type the leader and the amount, and writes nothing until the owner types `CONFIRMAR`. The release accepts a leader and an amount only as a pair that one of the two sources holds (the copy's leader with the copy's amount, or the last bid's leader with its amount), never a leader with zero or an amount with no leader, and the leader's committed money must cover it: a tampered lot can alter either the copy or the bids, so neither is trusted alone. It refuses a lot whose time is still running, a lot that is already settled or not active, a lot whose history verifies, and a blank or over-long decider or reason (the limits are checked before the transaction). It runs under the lot's row lock, then the leader's wallet, the order bidding uses. Migration `20261029000009_integrity_release.sql` adds the status `integrity_cancelled`, the append-only table `integrity_decisions` (one row per lot, unique) and its trigger. The leader's committed money covers this lot and every other active, unsettled lot the same wallet leads, so a release never frees money committed elsewhere; a case where both the lot's copy and the bids are altered is refused (the money stays committed), a declared limit. Without any settled lot to check the secret against, the function itself does not check it: only the script asks for SEGREDO, and a direct caller of the function has no such check. A wrong pick between the two sources has no undo: the decision is append-only and the lot is no longer active, so the money can only be restored by a manual correction of the wallet outside this table. This is a declared limit of the confirmation step. A lot cancelled by the auctioneer with bids (a copy altered to zero bids) has no release: only an active lot is released. A lot released because only its copy was altered keeps its last bids unpublished for ever (the publisher skips a lot that is not active), so its audit stays pending and its receipts never reach published: also a declared limit. The publisher and the bid path skip any lot that is not `active`; the auctioneer sees a released lot as cancelled; the winner and the public see the lot as not found (a known limit, the winner is not notified yet). The auctioneer sees only 'cancelled', without the reason: the owner tells them outside the system (a known limit). A lot with no bids whose copy holds an amount but no leader has no answer that frees it: settlement refuses it too, so it stays open (a declared limit). Tests: `owner-release.test.ts` (52 cases, including two simultaneous releases and a release racing a settlement).

## D21. Public anchor of the bid-chain head (GitHub now, timestamp service later)
Built so far: each accepted bid returns a bid receipt `{seq, head, placedAt}` in the response of `POST /api/lots/{id}/bids` (`BidAccepted` in the contracts); the pure rules of the anchor (`modules/anchor/rules.ts`); the GitHub client; and the publisher, run by the same per-minute cron as the settlement. The rest is planned and not built yet.
- **Chosen:** each accepted bid returns a bid receipt to the bidder, with its head hash (the "ponta"), sequence number and time. A separate publisher will write each lot's heads to a public, append-only repository, `RafalauriSantos/casa-de-leiloes-ancora`, in commits that only add lines (`lot_id, seq, head_hash, published_at`). The branch will be protected against force-push and deletion of history.
- **How it publishes (built):** one file per lot, `lots/<lot_id>.csv`, with the header `lot_id,seq,head_hash,published_at` and one line per bid. The publisher verifies the lot's whole chain and its head before publishing, never writes a line the anchor already holds, and refuses to go on if the anchor holds a different hash for a bid. Progress is kept in `lots.anchored_seq`, with `anchor_attempts` and `anchor_retry_at` for the retries. The mode is `ANCHOR_MODE` (`github` or `off`), with no default: the server does not start without it, so a forgotten setting cannot switch the anchor off unnoticed. `off` is for local development and tests.
- **How a run behaves (built):** the cron settles first and then publishes, so an anchor that fails or hangs cannot stall the settlement run itself; a payment still waits for the publication of its last bid (option B, below). A run stops starting lots after 5 seconds from its own start or 8 seconds from the start of the request, whichever comes first, and each GitHub call has a 4-second limit, because the per-minute job waits 20. A run takes a lot before working on it (`anchor_retry_at` holds it for 2 minutes), so two runs never publish the same lot; if a run dies, the lot is tried again after that time. Lots are taken by the age of their oldest unpublished bid; a lot whose next bid row is gone is taken first and fails its check, and counts as stale at once, so a broken history is never a silent gap. Every bid of the lot is checked against the anchor file, not only the new ones: a line that was published and is gone, or has another hash, or appears with two hashes, or a bid in the file that the history does not have, is an incident: that lot is not written, and the run goes on with the other lots. The 8-second bound leaves room for two 4-second calls inside the 20 seconds the job waits (the bound does not count time in the database). A refused token, a 404 on a write (wrong repository, branch or token access) or a rate limit stops the run. A file of more than 600 KB, or one that a new line would take past 600 KB, is never rewritten, and its lot does not advance (GitHub reads up to 1 MB through this API, and a write must finish inside one 4-second call): it is reported every run until someone looks. A line of another lot in a file is an incident too. What GitHub answers for a file it cannot read back is not in its documentation; the client treats an unreadable body as unavailable and a 403 that names `too_large` (from memory, not recorded) as too large, neither of which writes.
- **Known limits (declared):** the cron's answer is `{ settled, failed, anchor }`, not `{ code, message }`, like the settlement answer before it. This is an exception to the single error shape, accepted by the owner on 2026-10-24. Nothing reads that HTTP 500 except the job's own record in `net._http_response`: a real notification (an e-mail, a message) is not built. The lock that keeps the head and the bids consistent while reading (`for share`) has no test: the race is too narrow to reproduce reliably. GitHub documents secondary limits of 80 content-generating requests a minute and 500 an hour ("Rate limits for the REST API" on docs.github.com, checked on 2026-10-24); with many active lots at once the anchor will lag, and the stale alert will say so.
- **Existing lots in production:** every lot that already has bids starts as pending. They are published, with the time of the publication, not of the bid, and the cron answers 500 for a few minutes while the 20-lots-per-run backlog drains. They are published rather than skipped, because a lot that is never anchored can never be audited. This only works if `AUDIT_HMAC_SECRET` in production is the one those bids were hashed with: if it was ever rotated, those lots fail their verification on every run and the cron stays at 500. The first real publication is watched by hand, because the answers for a rate limit and for a file too large to read were written from memory, not recorded.
- **Availability first:** a bid is accepted when the database accepts it, and never waits for GitHub. The publisher retries with growing delays. Each publication is keyed by (lot, seq), so a retry never writes the same head twice.
- **Money waits for proof (built, 2026-10-25):** settlement does not move money until the lot's last head is published. The owner chose this on 2026-10-24 as option B in D22 and approved the design on 2026-10-25: a GitHub outage delays settlement, it never pays on unpublished history, and it never stops bids. The cron keeps its order, settle first and publish after (the owner's choice): a lot whose last bid was published in the same run waits for the next run, so a payment can come up to about a minute later than the end of the lot, and longer while GitHub is down. After 10 minutes of waiting the cron answers 500 (the stale head alert). **Declared limit:** nothing ends a wait by itself when the publisher can never publish the lot: a refused token (it also stops every other lot's publication), a file over the size cap, a history that fails the check, or a file that contradicts the history. The money stays committed and nobody is paid, the cron answers 500 every minute until a person fixes the cause, and the release of such a lot is D20 (built, run by the owner). A read of a lot that waits stays cheap: `settleLot` first looks at the lot without a lock and without checking its chain, and returns at once when the lot is not over, is already settled or cancelled, or waits for its publication; only a lot that may be settled takes the lock, which judges it again. The price is that a lot that is altered and not published waits for the settlement and is reported by the publisher instead: it refuses a history that does not verify (the run answers 500, again after each retry of 1, 2, 4, 8 and at most 15 minutes, and as stale after 10 minutes). *This replaces the temporary order accepted on 2026-10-24, in which a payment could come before the publication of its hash (D6).*
- **Audit states (replaced by D22, which gives the verdicts per lot; its `not_in_history` and `divergent` take the place of "missing"):** each bid will be "published" (its head is in the anchor), "pending" (not yet published; never shown as intact), or "missing" (a bid receipt's head is not in the anchor, which is evidence of tampering or of a publisher fault).
- **Lots with pending or divergent heads (D22):** a lot with a pending head stays active and unsettled until publication. It is a normal wait, so it is not counted as a failure by the cron until it has waited 10 minutes (D21, Resilience). When it has waited 10 minutes the cron counts it as stale and answers HTTP 500 (see Resilience); a notification to the owner is planned, not built. A lot whose head is `divergent` (D22, formerly "missing") is handled as in D20: it is never settled, and only the system owner decides what happens to it.
- **Declared limits:** the window between acceptance and publication is covered only by the bid receipt. Whoever controls the GitHub account can change settings, so the account needs strong authentication. The anchor is trust in GitHub, to be stated in the README before submission.
- **Resilience (approved by the owner on 2026-10-24, with these figures):** (1) an alert: a head that stays pending for 10 minutes or more is reported as an incident, by the cron answering HTTP 500 and a log line; (2) retries with growing waits after a failed publication: 1, 2, 4, 8 minutes, never more than 15; (3) a daily scheduled test that writes to the real anchor repository and fails loudly when GitHub changes its answers. For the tests, real GitHub answers are recorded once and served by a local server, the pattern the Met uses. The owner approved widening the rule "only the Met is stubbed" to the Met and the GitHub anchor repository (CLAUDE.md and the testing decision are updated).
- **Revisit later:** a free RFC 3161 timestamp service, or OpenTimestamps, as a second anchor. Free services have no availability guarantee, and their limits and prices change, so each option must be checked again before adoption.
- **Considered and not chosen now: Cloudflare D1 as the anchor.** D1 is independent of our database and testable offline (Miniflare runs a local D1), and a unique key on (lot, seq) would stop duplicates. It loses on public verification: nobody can clone it, so a third party cannot keep a copy that exposes a later rewrite, and the account owner can restore the database to an earlier point (Time Travel). It needs a Worker to write (the REST API is meant for administration and shares the account's global rate limit) and a public read Worker. GitHub needs less to build and is publicly replicable, so it stays the first anchor. D1 stays a candidate for a second anchor. Facts checked in the Cloudflare documentation on 2026-10-24.
- **Kept on the device:** the bidder's receipts are stored in the browser per bidder and lot, validated on read and merged on write, so they survive a reload. A bid whose response never arrives leaves no receipt; the anchor (above) is the real answer to that.
- **Status:** decided by the owner. Built: the bid receipt, the pure rules, the GitHub client, the publisher with its retries and the 10-minute stale count (the cron answers HTTP 500; no notification is sent yet), and the migration for the publication progress (applied to production only with the owner's explicit OK). Not built: the daily live test, the audit page's results and the settlement check, each with tests, and an explicit OK for each PR, because it touches money.

## D22. Public audit page (J7)
- **Decided by the owner on 2026-10-24.** Design approved. Built so far: the route `GET /api/lots/{id}/audit` with the bids, the chain result (slice 2) and the anchor result (slice 3: the read of the file in the order of D22, the cache of the pair, the call limit, the time budget, the branch check and the fresh re-read), the 404 and the 422 for a bad `head`, the receipt head result and the headline, decided on the server by one pure function so the page cannot claim more than was proven (slice 4). The page `/auditoria/{id}` is built too (slice 5), linked from the lot page and from each receipt the bidder keeps; its words are fixed per headline and tested so they claim no more than the headline proves. Settlement waiting for the publication of the last head (option B) is built too (slice 6). Where a sentence below says what the route or the page "will" do, that part is not built.
- **What it will be:** a read-only page and route that anyone can open without logging in. They will show the bid history of a lot and three separate results: the chain, the public anchor (D21) and, when asked, a bidder's receipt head. They change nothing. *Replaces the "Audit states" bullet of D21, which described per-bid states; the results here are per lot.*
- **Route and page:** `GET /api/lots/{id}/audit?head=<64 lowercase hex>` (already listed in D9) and the page `/auditoria/{id}`, linked from the lot page and from each receipt the bidder keeps. The page will read `?head=` from its own address. A `404 not_found` is answered only when no lot row exists for the id; a cancelled lot is audited like a live one (a legitimately cancelled lot has no bids and shows "sem lances"), because the status, `bid_count`, `head_seq` and even the bid rows are things a database writer can change, and a 404 would hide the tampering and keep a receipt from being checked. An invalid `head` answers 422 first, before the id is looked at (it costs nothing); then an id that is not a uuid or not in the database answers 404, before any GitHub call, so a random id costs no GitHub call. A `head` that is not 64 lowercase hex characters answers `422 validation_error` (hashes are stored in lowercase). An id that is not a uuid answers `404 not_found`, as the public lot read does.
- **Answer:** `bids` (seq, pseudonym, amount, time truncated to the second, hash), `chain`, `anchor` and `receiptHead` (only when `head` is sent). No name, e-mail, user id or secret. The list is not paginated. Declared limit: the anchor file is capped at 600 KB (about 4,500 bids), bids keep being accepted beyond it, and a lot past that size cannot be published (`too_large`), so the list is not bounded by the cap. Before option B (below) is built, the owner must decide between a per-lot cap on bids and a file split in chunks; option B must not ship while a lot can pass the cap and stay unsettled. The hash will be shown because the anchor repository already publishes it and it holds no personal data. For J7.4 ("no personal data, not even indirect"): the pseudonym and the time to the second are the tradeoff accepted in D10; the amount is already shown in the live room (D18).
- **Chain result:** `intact`, or `tampered` with `brokenAtSeq`, defined once: the lowest seq at which the stored history and the lot's copy of the head (`head_seq`, `head_hash`) disagree or the chain check fails (a seq above `head_seq` that the history holds counts as a disagreement). `firstBrokenSeq` in `shared/bid-chain.ts` returns it (built, with a test for each example below); settlement and the publisher use it for the chain and the head copy, and the audit route will too, so they decide alike; the old yes-or-no `chainIsValid` was removed. D20 needs the same number. Examples: bids 1, 2, 4 give 3 (the seq expected at the gap); an edited bid 3 gives 3; no bids with `head_seq` 5 give 1; bids 1 and 2 with `head_seq` 5 give 3; bids 1 to 4 with `head_seq` 5 give 5; bids 1 to 5 that verify with a copy that says `head_seq` 3 give 4; the same `head_seq` with a different `head_hash` gives `head_seq`; bids that exist with `head_seq` rewritten to 0 give 1. The result is `tampered` for any of these. A lot with no bids and `head_seq` 0 is `intact`; its anchor file is still read, and the anchor result is `published` only when the file is confirmed absent or holds no bid line; a bid line in it is `divergent` (the bids were deleted and the head reset).
- **Anchor result:** the file `lots/{id}.csv` of the anchor repository will be read and compared with the history.
  - `published`: every bid of the history is in the file with the same hash.
  - `pending`: (the missing file must be a confirmed 404, as below) the file lacks only the latest bids, which the publisher has not reached yet, and nothing contradicts it. A lot with bids and no file, with `anchored_seq` 0, is `pending`. The answer also says when the oldest unpublished bid is 10 minutes old or more: that is the D21 incident, not a normal wait.
  - `divergent`: the file holds a bid the history does not have (the last bid was removed after publication); or two different hashes for one bid; or a different hash for a bid; or a line of another lot or a line that is not a bid line; or a file that holds bid K+1 but lacks bid K, with K above `anchored_seq` (the publisher never writes that); or it lacks a bid at or below `anchored_seq`, including a missing file when `anchored_seq` is above 0. Before any divergence found by the comparison is reported, the read is repeated once after 1 second (the re-read repeats steps 1, 2 and 3 in that order, and the verdict uses the snapshot taken after the last file read; the re-read always calls GitHub, never the cache, and its pair replaces the cached one); if the file still lacks the bid, it is reported as `divergent`, and a failed second read gives `unavailable`.
  - `unavailable`: every failure that is not a confirmed missing file: GitHub unreachable, an answer that is not what GitHub documents, the token or the rate limit refused, any status the publisher's client calls `auth`, `rate_limit`, `unavailable`, `too_large` or `conflict`, or a file over 600 KB. The audit's read will get a distinct "not found" result from the client; the publisher keeps its own read, where a missing file means "create it" and a wrong repository or branch fails at the write (404 becomes `auth` and stops the run). A 404 is a missing file only when the repository and the branch are confirmed to exist (a second call to the branch endpoint, made by the audit); a 404 that cannot be confirmed is `unavailable`, because GitHub also answers 404 for a wrong repository, a wrong branch or a token without access. What the publisher calls `integrity` about the file's content (a bid the history does not have, a different hash, a lost line, a foreign line) becomes `divergent`; its history check is not used, because the audit makes its own chain check. The page never says `published` or `pending` for a file it could not read.
  - `off`: `ANCHOR_MODE=off` (preview and local runs); the page says the anchor is not configured.
- **Receipt head result (`receiptHead`):** `in_history` with its seq, or `not_in_history`, shown as "não encontrado neste histórico". The lookup compares the head with the stored hash of each bid. A real receipt is `not_in_history` when its own bid was removed (and the lot's head rewritten); a later removal does not change it (for that, the later bidder's receipt or the anchor is needed), and an earlier change leaves the stored hash in place, so it is the chain that fails then. A made-up or mistyped head gives the same answer, so the result says only that the head was not found.
- **Headline, in this order:** (1) the chain is `tampered` or the anchor is `divergent`: "adulterado", whatever the receipt says. (2) A `head` was sent and is `not_in_history`: "não confirmado" (never "adulterado", so a made-up head cannot accuse a lot). (3) The lot has no bids: "sem lances", and "âncora não verificada" as well when the anchor is `unavailable` or `off`. (4) The chain is `intact`, a `head` was sent and is `in_history` with seq N: "íntegro até o lance N" when the anchor is `published`, or "íntegro na cadeia até o lance N; âncora publicada só até o lance M" when it is `pending` (M is the highest seq of the bid lines read from the file; "nenhum lance publicado ainda" when M is 0). (5) The chain is `intact`, the anchor is `published` or `pending` and no `head` was sent: "sem divergência até o lance M publicado" (or "nenhum lance publicado ainda"), with the line that the bids after M and the removal of the last bid are covered only by a receipt. (6) The anchor is `unavailable` or `off`: "âncora não verificada", with the chain result (worded "cadeia sem quebra até o lance N", never a lot-wide "íntegro") and the receipt result, if a `head` was sent, on their own lines. A lot-wide "íntegro" is never shown, because the anchor cannot catch the removal of a last bid before its publication, and a receipt proves only the bids up to its own seq; that is the publication window declared in D21, in the README and on the page. A lot with no bids that is opened with a `head` says "não confirmado" (rule 2 comes before rule 3: no bid can have that hash), not "sem lances"; the page's wording for it must not read as an accusation.
- **Decision (publication window), chosen by the owner on 2026-10-24: option B.** Settlement waits for the publication of the lot's last head (built, D21), so money never moves on a bid whose hash is not in the public anchor; bidding keeps working when GitHub is down or limited, and only payment waits. The window itself stays: a last bid removed before its publication cannot be caught by the anchor, only by a receipt the bidder keeps; it is declared in the README and on the page. Rejected: making a bid wait for its publication (it closes the window, but GitHub down or limited would stop all bidding, and GitHub limits writes), and only declaring the window (it leaves the money unprotected). Because the window stays open, the headline rules above stay as written.
- **Read-back before payment (D21, decided by the owner on 2026-10-25: not built):** a second step would read the anchor file back a few minutes after publication and release payment only after it matches the lot's bids (a `verified_seq` gate). The brief asks that any later change to the history be detected by the audit, not that payment wait for a read-back; option B already keeps money off unpublished bids; and the deadline needs that time for the receipt page, the seed (D15), the end-to-end script and the daily live test. The gap it would close is the one in the README: if GitHub accepts a write and keeps other content, the money may have moved before the audit sees it. Declared as a limit.
- **Order of the reads (consistency):** the page will read, in this order, (1) the lot's `anchored_seq`, (2) the anchor file, (3) the lot row and its bids in one `repeatable read` transaction, without locks, opened only after step 2 ends (a transaction opened before the GitHub read would miss a bid published in between and show it as `divergent`). The verdict uses the `anchored_seq` of step 1 (or of the cached pair), never the one in the row of step 3, which supplies only `head_seq`, `head_hash` and the bids. The publisher writes the file before it raises `anchored_seq` and publishes only committed bids, so a bid placed or published between the steps shows as `pending`, never as `divergent`. This assumes that GitHub's Contents API returns a file it has just accepted; that is an assumption, not a checked fact, and the residual risk is accepted with the design: a stale read that survives the re-read can show a healthy lot as "adulterado" for a short time. Pinning the read to the commit the publisher wrote was considered and left out because it needs a new stored column. The single re-read above and the daily live test of D21 limit the harm, and neither proves it. The route never settles and never writes, so it differs from the other reads of a lot (D6).
- **Time budget:** the audit's GitHub work shares one budget of 8 seconds per request: once it has passed, the re-read and the branch confirmation are skipped and the anchor result is `unavailable`. Each call's time limit is the smaller of 4 seconds and what is left of the budget, so GitHub time is bounded by the budget plus the 1-second wait of a re-read, about 9 seconds before the database reads; the platform's function limit (300 seconds is the current Vercel default, a claim not checked in this repository) is far above that, and the page shows its loading state meanwhile.
- **Reading the anchor:** the audit uses the same GitHub client and the same file parser as the publisher (`parseAnchorFile`, moved to `anchor/file.ts` and exported with `readAnchorFile`, `confirmBranch` and `MAX_ANCHOR_FILE_BYTES`; it strips carriage returns, skips the header and blank lines, and checks the lot id and four fields), so a file saved with other line endings cannot show as `divergent` for one and valid for the other. The raw-file host was rejected: its cache can lag by minutes, and a lagging read would show a published bid as lost.
- **Cache and limit:** the pair (`anchored_seq`, file) of a lot will be cached together for 30 seconds in the memory of the server instance; caching the file alone would break the read order (a fresh `anchored_seq` against an old file shows a healthy lot as `divergent`). The database snapshot is always fresh, which is safe: the cached file holds only committed bids. A failed read is not cached. While the cached pair holds a line that GitHub has lost, the page can still say "íntegro até o lance N" for up to 30 seconds: a declared limit. Each instance will make at most 30 GitHub calls per minute for audits (cache misses, re-reads and branch confirmations all count); above that the anchor result is `unavailable`.
- **Tradeoff:** the audit uses the publisher's token, so audits share its GitHub limit (5,000 requests per hour for a token, a figure from GitHub's documentation that was not re-checked on this date). The cache and the cap bound each instance, but the total grows with the number of instances: 5,000 an hour is about 83 a minute, so three instances at the cap of 30 can use the whole limit, and a rate limit stops the publisher's run (D21). A flood could therefore slow publication, and with option B a slower publication delays settlement, that is, payments. The cap of 30 is per instance and does not bound the shared token quota. No token would give only 60 requests per hour per address (also not re-checked), and the platform's servers share addresses, so that was rejected.
- **Trust:** `anchored_seq` comes from our database. Someone who can write both the database and the anchor repository could lower it and remove a line; the page would then show `pending` until the 10-minute rule of D21 reports the stale head. That needs both accesses, which is outside the model the anchor defends against.
- **Tradeoff:** that the chain is intact comes from the server, because the chain is keyed (D4); a visitor cannot recompute it. The anchor lines are public, so a visitor can still compare the hash column with the repository.
- **States of the page and tests:** the page will show loading, error (the route failed; no result is shown) and empty (no bids) states. The build slice names a test for each rule above, including the read order with a publication between the steps, the cache pair, the 404 confirmation, the headline order and the receipt cases.
- **Not in this page:** the owner's release of a tampered lot (D20; its `integrity_cancelled` status is not in the answer yet), the wait for publication before settlement and the daily live test (D21).

## D23. A lot takes at most 1,000 bids
- **Decided by the owner on 2026-10-25** (accepting the recommendation). Built: the rule, the error, the room's notice and the tests below.
- **Chosen:** a lot takes at most `MAX_BIDS_PER_LOT` = 1,000 bids (`packages/contracts/src/limits.ts`). The 1,000th bid is accepted; the 1,001st is refused with `409 bid_limit_reached` and the message "Este lote atingiu o limite de 1.000 lances." (`BID_LIMIT_MESSAGE`, one text for the server and the room). The limit is judged by the pure `decideBid`, right after the lot's own state (cancelled, not started, ended) and before the "already leading" check, so it is the same for everyone, the leader included. The count is the lot's `head_seq` read under the lot's row lock, so two bids racing for the last place cannot both get it.
- **Why:** D21 and D22 publish one file per lot, capped at 600 KB (about 4,500 lines), and a lot past the cap could not be published. With option B (settlement waits for publication) such a lot would never be settled and its money would stay committed. 1,000 bids make a file of about 132 KB, under a quarter of the cap: a test keeps that true (`anchor/rules.test.ts`), so raising the limit without checking the file size fails the build.
- **Tradeoff:** a lot with 1,000 bids stops taking bids until its end, even when someone would pay more; the last leader wins at the amount of the 1,000th bid. Declared in the README. A file split in chunks was considered and rejected: it makes the publisher, the audit and the parser more complex for a case that a normal lot never reaches.
- **Room:** the live room shows the notice and hides the bid form when the lot is full.
- **Tests:** `decideBid` boundary (999 accepts, 1,000 refuses), order against the lot state, the leader's message; 1,000 real bids over HTTP then the 1,001st refused with no money moved and the audit intact; two parallel bids for the last place, exactly one wins; the room's notice; the anchor file size.

## D24. The sign-up chooses the role (B14, criteria 0.6 and 0.7)
- **Decided by the owner on 2026-10-26:** the sign-up asks "Quero comprar" (bidder, the default) or "Quero vender" (auctioneer), as real auction sites do; before this, every new account was a bidder and the only auctioneer came from the seed.
- **How:** the choice travels in the sign-up metadata (`role`). The trigger `handle_new_user` (migration `20261030000011`) reads it once, when the account is created: `auctioneer` gives an auctioneer, any other value or none gives a bidder. The role then lives only in `public.profiles`, which the API roles cannot write (no grant, RLS on, no policy), so editing the metadata later changes nothing. Every account keeps a wallet, because the settlement credits the auctioneer's.
- **Tradeoff:** anyone can open an auctioneer account, with no check of who sells. For a demo with simulated money this is the expected flow; a real house would review sellers before their first lot. The role cannot be switched later: a person who wants both needs two accounts.
- **Tests:** `me.test.ts` (the chosen role; a forged value and no value give a bidder; editing the metadata after sign-up does not change the role, proven by two hand mutations: a trigger that syncs the role on update, and a function that takes any value), `journey.test.tsx` (a seller signs up through the screen and gets the auctioneer panel, not a wallet).

## D25. Cancelling a lot with bids refunds the committed money (B19, criterion 9.1, an optional of the brief)
- **Chosen:** the auctioneer may cancel any lot that has not ended, with or without bids (the brief's base case, a lot without bids, is unchanged). In the same transaction, under the lot's row lock and then the leader's wallet lock (the order bidding uses), the leader's committed amount goes back to their available balance; outbid bidders were already released when outbid. Nobody is charged, nobody is credited, and no ledger row is written, because no money changed owner.
- **Screen:** for a lot with bids, the first click shows what will happen and asks for "Confirmar cancelamento"; a lot without bids is cancelled at once, as before.
- **Effects:** the lot leaves the showcase and its room, later bids are refused (`lot_cancelled`, or `not_found` for a bid that reads the lot after the cancel, as its public page does), the bidders see it as cancelled in "Meus arremates", and the audit page still opens. The publisher only publishes active lots, so bids not yet published when the lot is cancelled stay unpublished; no money depends on them.
- **Tradeoff:** the auctioneer can withdraw a lot at the last second, after bidders committed money and attention; the leader loses the chance to win, though not money. A real house would limit or charge late withdrawals; here the refund is the whole rule.
- **Checks before the refund (after the reviews of 2026-10-26):** the refund moves money outside the settlement, so it takes the same guards. The lot's history must verify and the lot's copy of its leader and amount must match the last bid (`verifiedLead`, the settlement's own check, exported for this); the leader's wallet must still cover this lot plus the other active lots they lead, so a refund never frees another lot's money (the release of D20 has the same guard). A failed check refuses the cancel with `internal_error` and moves nothing; such a lot is left for the owner's release (D20). Whether a refund is due also comes from the verified bids, never from the lot's `bid_count` copy: a copy zeroed by a database writer would otherwise cancel the lot without the refund and strand the money where the owner's release, which takes only active lots, cannot reach it (found by the Codex review of #45).
- **Tests:** `cancel-refund.test.ts`: the leader's committed money back at once, totals unchanged, no ledger row, a later bid refused with no money moved; only the cancelled lot is refunded when the leader leads two; a `bid_count` copy rewritten to 0 still refunds the leader; a copy that disagrees with the last bid, a forged bid with a matching copy, and a wallet that cannot cover the leader's other lots are each refused with no money moved; an ended lot with bids and a lot the owner already released are refused; a cancel racing with five bids leaves no committed money. Five hand mutations were each caught: the refund clearing all the leader's commitment, trusting the copy without the chain check, dropping the guard for the other lots, treating a released lot as open, and letting an ended lot be cancelled. Also `results.test.tsx` (the panel asks to confirm and names the refund) and `rules.test.ts`.

## D26. Docker Compose for the app, on top of the Supabase CLI (B20, criterion 9.2, an optional of the brief)
- **Chosen:** `docker-compose.yml` runs the API and the site from one image (`Dockerfile`, `npm ci` inside it), with `network_mode: host`. Supabase stays on its own CLI (`make db-up`), which also runs on Docker. `make compose` fills the variables from the running stack through `scripts/with-local-env.sh`, as `make dev` does; a missing variable stops the compose (`${VAR:?}`), never a default secret.
- **Why not Supabase inside the compose:** the app needs real Supabase Auth (sign-up, sessions, the JWKS the API checks). Rebuilding it by hand (the Supabase Postgres image, the Auth server, a proxy for `/auth/v1`, signing keys) would be a second copy of Supabase to keep in step with the hosted one, for no gain in what the app proves.
- **Why host networking:** the local Auth signs tokens with the issuer `http://127.0.0.1:54321/auth/v1`, and the API refuses any other issuer (the JWT check, see "Supabase Auth" above). Inside a bridge network the API would reach Auth under another name and refuse every token.
- **Tradeoff:** Node is still needed on the host, for the Supabase CLI (`npx supabase start`). Host networking works on Linux; on Docker Desktop (Mac, Windows) it must be turned on in its settings (version 4.34 or later). Production does not use this: it runs on Vercel.

## D28. Catalog search pages through the Met's results, 12 at a time (B24)
- **What the Met does (measured on 2026-10-26, live):** a search returns at most 100 ids by default and accepts `offset` and `limit` (up to 500 per answer). Its answers are exact: `offset=12&limit=12` returns the 13th to the 24th id. A search reaches at most **10,000 results** (offset 10,000 is empty), so the collection's 371,179 public-domain objects with an image cannot all be reached through search.
- **How:** the search asks the Met for one page (`offset` and `limit` = 12), then fetches the details of that page's ids only. The response is a page: the items, the total the Met has, the page, the number of reachable pages (the total, up to 10,000, in pages of 12) and whether there is a next page. A page past the last reachable one is empty. Page numbers that are not positive whole numbers are refused with 422.
- **Why not import the collection:** importing the whole collection would be hundreds of thousands of requests to the Met and a large database, which does not fit the delivery date, and it would copy objects no one bids on. Paging keeps search live, against the real answers.
- **Tradeoff:** a page costs 12 detail requests to the Met, so a search is slower than the first page was. A page can show fewer than 12 items: the Met's search says an object has an image, but its detail sometimes has no small image (measured: 5 of the 12 ids of page 9 of "vase" have one). Those objects are left out, as before, never shown broken. Searches with more than 10,000 results show a note that only the first 10,000 are reachable. The catalog still depends on the Met for search, as the brief allows; a lot copies its item when it is created.
- **Correction of an earlier version of this decision:** an earlier draft said the search fetched every matching id and reached 371,179 objects. That was wrong: the Met answers only 100 ids per request by default, and the window is 10,000. The code now uses `offset` and `limit`.
- **Tests:** `catalog.test.ts` ("pages through every result", the empty page past the end, the ninth page, the 422 for a bad page), with the Met stub answering the real captured page for each offset and limit (`backend/tests/fixtures/met`), and a real closed answer for any page not captured. `catalog-states.test.tsx` (the total, the next and previous page, the 10,000 note).
